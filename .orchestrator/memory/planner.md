## Decisions affecting my role
- This project's `stacks:` is `none` — every task in a Konnect tasks.md must carry a literal `Stack: none` line at column 0 (not indented under the checkbox item), matching the grader's `grep -c "^Stack: none"`.
- `openspec` CLI (not `orc`) is what actually exposes `status --change <name> --json`, `instructions <artifact-id> --change <name> --json`, and `validate --changes <name> --json`; `orc` only wraps `new change`/`init`. Run these from the Konnect repo root — running them from inside the change directory fails with "Change not found".
- Konnect's `config` toolset persists arbitrary JSON (`default_user_config()` in `crates/konnect-core/src/tools/config.rs`), not a fixed Rust struct — new integration-specific config keys (e.g. a new external tool's interpreter path) belong there as a new top-level JSON object, not in `ServerConfig`.
- `crates/konnect/tests/asset_references.rs` mechanically enforces 6 things for any new skill/agent: reference-file reachability from its parent SKILL.md, agent frontmatter preloading only real bundled skills, the top-level `konnect/SKILL.md` naming every agent by filename stem, `load_toolset(...)` examples naming real toolsets, trailing-comment tool names belonging to the toolset they're listed beside, and `tool(arg, ...)`-shaped examples using only real schema properties (all required ones present). Design/tasks for any new Konnect skill+agent must address all 6 explicitly.

## Gotchas found here
- Spec revision after a QA/reviewer round that flags "no runnable check" scenarios: rewrite each flagged scenario's THEN clause to name the exact verifying artifact (file + section heading, or an existing test's literal name) rather than restating the requirement more strongly. If no test exists for a prose-level claim, say so explicitly in the scenario — inventing a "verified by" citation for evidence that doesn't exist is worse than an honest gap (Article IV, No Invention, applies to spec text too, not just code).
- When a binding orchestrator decision says "delete key X from the change" but X is still live in already-implemented code/assets, the planner's job is to remove it only from planning docs (spec/design/tasks) and say explicitly in the handoff that the matching code/asset deletion is separate, unscheduled dev work — do not silently imply the deletion is complete everywhere.
- When an acceptance line's prose enumerates fields ("all three fields") and one field is deleted from the surrounding config example, update the count word too (e.g. "all three" -> "both") — leaving a stale count is a cheap, easy-to-miss inconsistency a grep-based grader won't catch but a human reviewer will.
- When a change adds fields to an existing content-hash's covered-key list (Konnect's `review_map_content_hash` pattern, `photo_intake.rs`), the two options are "accept the break, update the pinned-digest literal with a stated reason" or "keep old digests stable." Default to stable unless the brief says otherwise: make the new fields' inclusion in the hash conditional on `Value::get(...).is_some()` rather than always-insert-with-null-default — this makes the archived pinned-digest test pass *unmodified* (its fixture never had the new fields, so its bytes don't change) and costs nothing but one `if let Some` per new field. State this explicitly as "the projection is conditional; the existing test needs no edit" in design.md so the dev agent doesn't go looking for a literal to update that no longer needs one.
- When the coordinator sends a mid-task scope addendum that references a worked example (a prior handoff/prototype), read that document in full before folding the addendum in — the worked example usually names concrete claim *shapes* (e.g. "hypothesis A vs B with different confidences", "two counting methods that disagree") that a paraphrased addendum summary won't reproduce, and a schema built from the paraphrase alone will be missing fields the example already proved were needed.
- `openspec validate`'s "must contain SHALL or MUST" check can false-negative on a requirement whose body opens with backtick-quoted subject(s) before the modal verb (e.g. `` `agent-a`, `agent-b` SHALL ... ``) even though SHALL is present in the text — reword to open with a plain subject ("The system SHALL ...", matching every other requirement in the file) rather than debugging the checker.
