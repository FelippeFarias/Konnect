3. **3.2/3.4/3.5:** `save` normalizes through the struct, hashes the object it is about to write, and sets `approved` only when the prior on-disk `content_hash_at_approval` matches; the payload's `approved`/`approved_at`/`content_hash_at_approval` are never read. `approve` is the only producer of `approved: true`, recording `approved_at` (RFC 3339 UTC) and the hash of the value it just read.
4. **3.3 + orchestrator decision:** `load` returns `{map, approval_valid, saved_path}` with `approval_valid` computed server-side (`approved == true && hash == content_hash_at_approval`); the tested edit-the-file case shows `map.approved: true` alongside `approval_valid: false`. **4.1-4.3:** `ToolsetMeta{name: "photo_intake", category: "integration", tool_count: 5}` + the `build_tools_for` arm, and `photo_intake_exposes_exactly_its_five_tools_in_order` asserts the order through both `registry::tools_for` and `ToolRouter::load`.
5. **Three deliberate decisions the design left open.** (a) A revoking save **clears** `approved_at`/`content_hash_at_approval`, so an edit-then-undo cannot silently restore the gate — only a new `approve` call can (tested). (b) `save` refuses a `map_id` whose directory no scan minted (D13 rule 3), so tests create it through `prepare_map_dir` exactly as `scan_pcb_photo` does. (c) `nets[].source` is validated against `traced|inferred|manual`; `scale_reference.kind` deliberately is not (nothing consumes it until Slice 2).

## Deferred findings

1. `save` writes `approved: true` when the content hash matches the stored one, which is D5 as written but means a *save* can be the call that restores the flag after an unrelated no-op save. It is only reachable when the content is byte-identical to what a human approved, and `approved_at` still carries the original decision's time.
2. The `map` argument of `save_photo_review_map` is schema-typed as a bare `"object"`: the nested shape is enforced in Rust (`validate_incoming_map`) because a top-level JSON Schema keyword cannot reach `map.map_id` (D13). A caller therefore gets a serde error message, not a schema error, for a malformed map.
3. `scale_reference.kind` accepts any string (see Result 5c). If Slice 2's open question #1 (validating the scale against matched footprint dimensions) lands, that is where the vocabulary should close.
