## Result

### 1. Exact on-disk / stdout output of `scan`, `solve`, `cross-board --json`, `identify --json`; what `learn` persists

- `retrace scan <img> --format json -o <dir>` → `AnalysisResult.save()` writes **one file only**, matching `fmt` (never all three at once): `json`→`<dir>/analysis.json`, `csv`→`<dir>/components.csv`, `svg`→`<dir>/annotated.svg`. `analysis.json` = `{version, timestamp, image, components:[...], traces:[...], pattern_matches:[...], summary:{...}}`. `Component` = `{id, label, confidence, bbox:[x,y,w,h] (int, **pixels**), marking, part_number, datasheet_url, value, package}`. `Trace` = `{id, points:[[x,y],...] (int **pixels**), width_px (float), from_component, to_component}`. `components.csv` has no trace data. **Gotcha:** `AnalysisResult.board_dimensions` and `layer_count_estimate` are dataclass fields but are **not** written into `analysis.json` or `summary()` at all — a Konnect wrapper needing board width/height in px must read the source image itself, not retrace's JSON. Source: `src/retrace/core/pipeline.py` (`AnalysisResult`, `Pipeline.run`, `.save()`), fetched via `gh api repos/ericrihm/retrace/contents/src/retrace/core/pipeline.py -H "Accept: application/vnd.github.raw"`.
- `scan` **without** `-o` prints `json.dumps(result.summary(), indent=2)` to stdout — this is the "machine-readable stdout mode," but it is a summary only (counts, `components_by_type`, `duration_seconds`), not the full component/trace list. Full detail requires `-o` + file read-back. Source: `src/retrace/cli.py` `scan()`, lines 31-58.
- `solve` has **no `--json`**. It prints a text report (net assignments, inferred connections, ambiguous nodes, conflicts) to stdout; `-o file.txt` writes the same text, not structured data. Source: `src/retrace/cli.py` `solve()`, lines 236-304.
- `cross-board --json` prints JSON to **stdout only** (no `-o`/file option exists for this command): `{components:int, matches:[{pattern,score,partial,description,roles}], coverage:float, novel_components:[id,...]}`. Source: `src/retrace/cli.py` `cross_board()`, lines 356-432.
- `identify <marking> --json` prints the matched part dict, or `{"match": null, "query": marking}` (exit code 1) on no match, to stdout. Source: `src/retrace/cli.py` `identify()`, lines 158-183.
- `learn` persists new entries to `~/.local/share/retrace/learned_components.json` (`LEARNED_DB_PATH`) via `retrace.identification.matcher.learn_component()` (load-append-write). This is a **third, separate** global store from two others the pipeline writes automatically on **every** `scan`/`solve`/`cross-board` run (when `enable_learning` defaults True): `~/.local/share/retrace/knowledge.json` (`component_frequency`, `board_sightings`, `sourcing_queue`, written by `src/retrace/learning/engine.py`'s `record_detection`/`queue_for_sourcing`, invoked from `Pipeline._record_learnings`) and `~/.local/share/retrace/cross_board.json` (persisted `CrossBoardEngine` state, written by `Pipeline._run_cross_board`). All three live under the OS user's home directory (`Path.home()`, no env-var override), **not project-scoped** — a real cross-project/cross-user state-pollution risk for a Konnect wrapper. Sources: `src/retrace/learning/engine.py`, `src/retrace/identification/matcher.py` (`learn_component`, line 3010), `src/retrace/core/pipeline.py` (`_run_cross_board`, `_record_learnings`).

### 2. Windows install reality; OpenCV-only fallback; bundled fixtures

- Core runtime deps are `click>=8.1, numpy>=1.24, opencv-python>=4.8, Pillow>=10.0, requests>=2.31` — all ship Windows wheels on PyPI; the ML extras (`[detection]`=ultralytics/onnxruntime/scikit-image, `[ocr]`=easyocr, `[web]`=gradio) are optional and not required for `scan`'s contour fallback. `pip install git+https://github.com/ericrihm/retrace.git` should therefore work on Windows/Python 3.12 for the base install. **However**, `.github/workflows/ci.yml` only runs `runs-on: ubuntu-latest` across Python 3.10–3.13 — there is **no Windows CI job**, so this is inferred from pure-wheel dependencies, not verified upstream. Sources: `gh api repos/ericrihm/retrace/contents/pyproject.toml` and `.../.github/workflows/ci.yml` (both `-H "Accept: application/vnd.github.raw"`).
- `Pipeline._detect_contours` (used automatically when `ultralytics`/`onnxruntime` aren't importable) does adaptive-threshold + `cv2.findContours`, and classifies purely by bbox aspect-ratio/area into 4 buckets (`connector/ic/capacitor/resistor`) with a **fixed `confidence=0.5`** on every hit — no marking/value/package/part_number is ever produced by this path. README states only qualitatively that it is "less accurate but runs anywhere Python runs" (Design Decisions section); the only *numeric* accuracy figures in the README (89% OCR marking match, 24.3% ID rate, 40–70% trace recovery) are for the **full YOLO+EasyOCR pipeline on the synthetic demo boards**, not for the contour-only fallback. Sources: `src/retrace/core/pipeline.py` `_detect_contours`; README "Design Decisions" and "Known Limitations" sections (`gh api repos/ericrihm/retrace/readme -H "Accept: application/vnd.github.raw"`).
- No `tests/fixtures/*.jpg|png` directory exists anywhere in the repo (confirmed via full recursive tree listing, `gh api repos/ericrihm/retrace/git/trees/main?recursive=1`); all unit tests synthesize images in-memory (`tests/test_pipeline.py::_make_synthetic_image`, numpy/PIL) or mock `cv2`/pipeline internals — **zero real-photo fixtures ship in `tests/`**. `docs/examples/` does ship two ready-to-run demo PNGs, `docs/examples/xbox_board.png` and `docs/examples/cisco_board.png`, but the README's "Known Limitations" section states explicitly these are **synthetic PCB renders**, not photographs, chosen specifically to dodge the fact that the real iFixit teardown photos it also ships (`docs/examples/xbox_one_motherboard.jpg`, `xbox_one_motherboard_back.jpg`) are licensed **CC BY-NC-SA 3.0** (per README "Legal" section: "iFixit images — used under CC BY-NC-SA 3.0"), i.e. **not MIT and not redistributable inside Konnect's repo**. Net effect for Konnect: no accuracy-grade real-photo fixture exists to borrow; `xbox_board.png`/`cisco_board.png` (synthetic, presumably MIT like the rest of the repo) are usable only as a pipeline-plumbing smoke-test input, not for validating detection accuracy on real photographic noise/glare/perspective.

### 3. KiCad netlist import path; kicad-cli capability; Konnect's existing copper-mutation tools

**(a) Schematic vs. pcbnew import — confirmed via KiCad's own documentation:** netlist import (legacy "File → Import → Netlist" workflow) is a **PCB Editor (pcbnew) feature only**. KiCad 9.0 pcbnew docs, "Starting from a schematic" section: *"Update PCB from Schematic is the preferred way to transfer design information from the schematic to the PCB. In older versions of KiCad, the equivalent process was to export a netlist from the Schematic Editor and import it into the Board Editor."* — i.e. the netlist always flows schematic→PCB, into an existing board's footprints/nets, never into the schematic editor. There is **no netlist-import feature in eeschema** in any KiCad version, confirmed on the KiCad support forum: *"You don't import [a netlist into eeschema], you just open the file"* and *"there is no existing plugin or code that addresses the problem of getting a correct but possibly ugly schematic out of a KiCad netlist"*. Sources: https://docs.kicad.org/9.0/en/pcbnew/pcbnew.html ; https://forum.kicad.info/t/how-to-import-a-kicad-netlist-into-kicad-eeschema/13178 .
**(b) kicad-cli 9.0/10.0 has zero netlist-import subcommand.** Full inventory: `pcb {drc, export {brep,drill,dxf,gencad,gerber,gerbers,glb,ipc2581,ipcd356,odb,pdf,ply,pos,step,stl,svg,vrml,xao}, render}`; `sch {erc, export {bom,dxf,hpgl,netlist,pdf,ps,svg}}`. Netlist only flows out (`sch export netlist`); there is no `pcb import netlist` / `sch import netlist` command anywhere. Source: https://docs.kicad.org/9.0/en/cli/cli.html .
**(c) Konnect already exposes the copper-mutation primitives needed** — confirmed by grep of `crates/konnect-core/src/tools`: `route_trace` (`pcb_routing.rs:60`, via KiCAD IPC, `.with_board_access(BoardAccess::LiveOnly)`), `add_via` (`pcb_routing.rs:98`), `add_zone` (`pcb_board.rs:1233`, tries live KiCAD IPC first and refills, falls back to raw S-expression insert with a warning when no live KiCad is attached, and refuses binding copper to an undeclared net), `set_component_placements` (`pcb_components.rs:1879`, batched X/Y/rotation update in mm, one live-IPC undo step or a revision-checked file edit otherwise). All four already exist and are exactly the primitives a photo-trace-polyline→copper pipeline needs (`route_trace` per extracted polyline segment, `add_via` at layer transitions, `set_component_placements` from photo bbox centers × scale, `add_zone` for pours). No new KiCad-side wrapper is required — the only missing piece is entirely upstream: turning retrace's pixel-space `analysis.json` into mm-space nets/positions.

### 4. Prior art for photo/scan → PCB reconstruction

1. **pcbre** (davidcarne/pcbre) — https://github.com/pcbre/pcbre — "an open source package for semiautomated and manual PCB reverse engineering" from photos/scans; repo's own README states *"PCBRE currently doesn't have any documentation"*, so its scale-calibration/top-bottom-alignment mechanics could not be confirmed from docs (would require source inspection, out of this brief's scope/budget — deferred below).
2. **lukasloetkolben/pcbRE** — https://github.com/lukasloetkolben/pcbRE — MIT, pure-Python (numpy/Pillow/Tk, no native deps): load top+bottom photos, mirror the bottom image, click matching **vias** as control points (3 pairs → affine transform, 4+ → perspective homography) to register the two sides and transfer pad labels between them. Confirmed **pixel-only** — it does no mm-scale calibration.
3. **OpenBoardView** — https://github.com/OpenBoardView/OpenBoardView — a viewer/annotator for pre-existing `.brd`/boardview dump files (produced by dedicated boardview scanners), not a photo→netlist pipeline; per retrace's own comparison table, input is `.brd` files, with no detection or trace-extraction stage of its own.
4. **tracespace** — https://github.com/tracespace/tracespace — Gerber file renderer/converter ("render only" per retrace's comparison table); relevant only as a downstream viewer, not photo-based, no scale-from-photo step.
5. **Kleber et al., USENIX WOOT 2017**, "Automated Reverse Engineering of PCBs from Photographs" — https://www.usenix.org/system/files/conference/woot17/woot17-paper-kleber.pdf — the closest academic precedent (per retrace's own README "Prior Work" table), 8 years old with no public follow-on tool; and **Kleber et al. 2024**, Scientific Reports, 3D X-ray-CT netlist extraction for inner/buried layers — https://www.nature.com/articles/s41598-024-84635-2 — cited directly by retrace's README as the only known answer for inner-layer traces, which retrace itself explicitly does not attempt ("No inner-layer analysis... require X-ray CT imaging").
6. **KiCad's own manual-trace aids**: pcbnew supports dropping a raster PNG directly onto the board canvas as a scalable/lockable reference graphic for manual trace-over work (KiCad forum, "Add image to PCBNew for Reverse Engineering of Layout" — https://forum.kicad.info/t/add-image-to-pcbnew-for-reverse-engineering-of-layout/22853 ), plus the bundled `bitmap2component`/"Bitmap to Component" utility that converts a bitmap into a silkscreen-only footprint graphic. Neither does automatic trace extraction, netlist inference, or scale calibration — both are pure manual-tracing aids.

Scale calibration and top/bottom alignment handling per tool (from what's documented): pcbre — undocumented; pcbRE (lukasloetkolben) — no mm calibration, via-click affine/homography registration only; OpenBoardView/tracespace — not applicable (no photo input); Kleber 2024 — solves inner layers via X-ray CT rather than optical calibration; KiCad image-overlay — fully manual, user drags/scales the bitmap by eye, no calibration tooling.

### 5. mm/px calibration and top/bottom multi-view registration techniques

- **retrace's own scale handling is a flat manual multiplier, not calibration-from-image**: `export-kicad-pcb --scale` (mm-per-pixel, default `0.1`) is applied uniformly to every bbox in `_px_to_mm`/`generate_kicad_pcb`; it never measures any reference object in the photo itself. Source: `src/retrace/cli.py` `export_kicad_pcb()`; `src/retrace/export/kicad.py` (`_MM_PER_PX`, `_px_to_mm`, `generate_kicad_pcb`).
- **Standard manual calibration techniques** (general, cited): place a ruler or an object of known physical size in-frame and derive px/mm from it; or use a component of a standardized package as an in-photo ruler once identified — e.g. an 0805 passive, whose KiCad footprint name literally encodes the metric size (`Resistor_SMD:R_0805_2012Metric` = 2.0mm × 1.2mm), confirmed directly in retrace's own `_PACKAGE_TO_FOOTPRINT` table (`src/retrace/export/kicad.py`); or use a known board-edge/mounting-hole spacing. Cited generally: Stanford EE368, "Reverse Engineering of Printed Circuit Boards" — https://stacks.stanford.edu/file/druid:np318ty6250/Johnson_Reverse_Engineering_PCBs.pdf ; industry PCB-RE process guide — https://www.pcb-hero.com/blogs/lickys-column/pcb-reverse-engineering-the-complete-guide .
- **Top/bottom registration**: mirror the bottom-side photo horizontally, then register the two images using shared physical landmarks (through-hole vias, mounting holes, board-edge corners) as control points — 3 point-pairs give an affine fit, 4+ give a full perspective homography. This is exactly what `lukasloetkolben/pcbRE` implements (https://github.com/lukasloetkolben/pcbRE), and mirrors the general "≥2 diagonal fiducials define translation+rotation, 3 in an L-pattern recommended" registration principle used in SMT fiducial alignment (https://jlcpcb.com/blog/pcb-fiducials), applied here to board-drilled vias/holes instead of dedicated SMT fiducials.
- retrace has **no built-in multi-image fusion**: `Pipeline.run(image_path: str) -> AnalysisResult` takes exactly one image and returns one independent result; there is no top/bottom pairing API. Konnect must implement mirroring + via-based registration itself, consistent with the analyst brief's Slice-3 default #4. Source: `src/retrace/core/pipeline.py` `Pipeline.run`.

## For the next agent

- **Integration shape**: wrap retrace as a Rust subprocess module mirroring `crates/konnect-core/src/tools/cli.rs` (kicad-cli) / `freerouting_mcp.rs` (Freerouting) — typed structs parsed from JSON, a `check_retrace` capability probe, exposed as a new/extended toolset in `router/registry.rs`. Always invoke `scan`/`solve`/`cross-board` with `-o <tmpdir>` and read the written file back (not stdout) except for `cross-board --json` and `identify --json`, which are the only two commands with clean single-shot stdout JSON.
- **Never let retrace write into KiCad files directly.** Its `.net` (`export-kicad`) uses synthetic, arrival-order pin numbers (`_build_nets` in `export/kicad.py`) that do not reflect real component pinouts, and even if they did, KiCad has no path to import a netlist into a *schematic* (finding 3a/b) — feed retrace's `ref→ref` connectivity into Konnect's own `sch_wiring` tools against real symbol pin maps instead, matching the analyst brief's default #6. Likewise, treat `export-kicad-pcb`'s `.kicad_pcb` as throwaway: read `analysis.json` bboxes directly and drive Konnect's existing `set_component_placements` (mm) after applying the user-supplied scale.
- **Global state risk**: retrace writes three separate JSON stores under the OS user's home directory on every run (`knowledge.json`, `cross_board.json`, and `learn`'s `learned_components.json`), with no env-var override (`Path.home()` only). Scope `HOME`/`USERPROFILE` per subprocess invocation (or accept and document the cross-project pollution) before shipping.
- **Hard limits to design around**: single-photo pipeline (no multi-view fusion — Konnect must implement top/bottom mirror+homography registration itself, finding 5); no inner-layer support ever (by design); OpenCV-only fallback yields fixed confidence 0.5 and only 4 coarse type buckets with no marking/value/part; 40–70% trace recovery is the pipeline's own stated ceiling *with* the full ML stack, demonstrated only on synthetic renders, not real photos; 128-part hardcoded ID DB; Windows path is plausible from pure-wheel deps but unverified by upstream CI (ubuntu-only).
- **Scale calibration is always a required user input** (retrace never derives it) — the analyst brief's default #3 (board-edge or known-package reference, e.g. 0805 = 2.0×1.25mm) is the right call and is now confirmed against retrace's own `_PACKAGE_TO_FOOTPRINT` table.
- **License care**: retrace's real iFixit teardown photos (`docs/examples/xbox_one_motherboard.jpg`/`_back.jpg`) are CC BY-NC-SA, not MIT — never copy these into Konnect's repo as fixtures; the synthetic `xbox_board.png`/`cisco_board.png` are usable only as plumbing smoke-test input, not accuracy validation.
